# Findings — `llm_d_sc`, a semantic-classification filter for Praxis

Written against [praxis-proxy discussion #1017](https://github.com/orgs/praxis-proxy/discussions/1017),
which asked three questions. This is a proof of concept that answers them with running
code and measurements rather than opinion.

**Nothing here has been pushed anywhere.** Two local branches exist for review.

---

## The three questions

### 1. "Is the filter chain the appropriate insertion point for network-calling enrichment?"

**Yes, and it needs no new machinery.** Every extension point required already exists:

| Need | Existing Praxis mechanism |
|---|---|
| See the prompt before routing | `BodyAccess::ReadOnly` + `BodyMode::StreamBuffer` → the protocol layer pre-reads the whole body **before** the header-phase pipeline, so `ctx.buffered_request_body` is complete in `on_request` |
| Choose a backend from it | `selects_cluster()` / `selected_clusters()` → set `ctx.cluster`, `load_balancer` consumes it |
| Ship it without touching Praxis | `export_filters!` + `[package.metadata.praxis-filters]` → `server/build.rs` auto-discovers it via `cargo metadata` |

**The entire Praxis-side diff for a working, traffic-serving integration is three lines
in `server/Cargo.toml`** (one dependency + two comment lines).

### 2. "What failure semantics should apply when the classifier reaches capacity?"

**Fail open by default; fail closed by configuration.** Measured, not asserted:

| Failure mode | p50 added latency | Outcome |
|---|---:|---|
| classifier down (connection refused) | **0.186 ms** | 100% HTTP 200 via `default_cluster` |
| classifier slow (500 ms stub, 100 ms budget) | **104.0 ms** | budget honoured within 4 ms; 100% HTTP 200 |
| queue exhausted (c=300, real classifier) | 430 ms | 40/300 `RESOURCE_EXHAUSTED`, **all still 200** |
| `on_resource_exhausted: reject` | 0.107 ms | clean 503s, no hangs |

The first row is the one that matters. A fail-open path that still waits the full
timeout on every request has already taken the gateway down; a refused connection must
cost approximately nothing, and it does.

Fail-closed exists for deployments where an unclassified prompt must not reach a model —
sensitivity-gated egress being the obvious case.

### 3. "Standalone, feature-gated in-tree, or a backend-agnostic interface?"

Both of the first two were built, so the comparison is a diff rather than a debate.

| | Phase A: standalone crate | Phase B: in-tree, feature-gated |
|---|---|---|
| Praxis diff | **3 lines** (`server/Cargo.toml`) | 24 files, +3484 / −7 |
| Default build cost | zero | zero — verified: 0 generated files, 0 tonic/prost rlibs with the feature off |
| Tests | 90 in-crate | 1801 filter-crate tests green (81 are `llm_d_sc`), 542 integration |
| Docs | hand-written | generated by `cargo xtask generate-filter-docs` |
| Branch | `poc/phase-a-external` | `poc/phase-b-in-tree` |

No opinion is offered on which should be adopted; that is a project-governance call.
The measurements are identical either way because the code is the same.

## What was built

```
client ──POST /v1/chat/completions──> Praxis
              pre-read body (StreamBuffer, complete, one chunk)
                        │ on_request
                ┌───────▼────────┐
                │ llm_d_sc       │ 1. extract prompt from messages[]
                │                │ 2. gRPC classify ──h2c──> llm-d-sc :50051
                │                │ 3. label → cluster (from Praxis config)
                │                │ 4. ctx.cluster = …
                └───────┬────────┘
                ┌───────▼────────┐
                │ load_balancer  │──> small / large / general
                └────────────────┘
```

llm-d-sc returns ranked labels and **no route field** — the routing decision is made in
Praxis, from Praxis config. That boundary is preserved exactly as #1017 describes it.

**llm-d-sc was not modified.** The `proto/classify.proto` in this repo is byte-identical
to upstream, asserted by a test that fails if it drifts.

## Findings for the Praxis maintainers

### F-1. Filter conditions cannot branch on a routing decision

`should_execute` evaluates `ConditionMatch { path, path_prefix, methods, headers }`
against `Request { headers, method, uri }` — the **original downstream request only**.
A condition cannot see `ctx.cluster`, `ctx.filter_metadata`, or headers set by an earlier
filter in the same chain (`filter/src/condition/request.rs`).

A filter that wants to act on a classification must therefore read the context itself.
`credential_injection` already does exactly this (`ctx.cluster` → per-cluster secret), so
the composition works — but it is not expressible declaratively in YAML, which is where
an operator would expect to express it.

> An earlier draft of this document claimed per-cluster credential injection was
> impossible in Praxis today. **That was wrong** and is corrected rather than quietly
> replaced, because the wrong version prescribed the less safe design (sending every
> backend's credential to every backend).

### F-2. `router` and any other cluster selector are mutually exclusive in a chain

`check_conflicting_cluster_selectors` makes two cluster-selecting filters before one
`load_balancer` a **config-validation error**. Verified against the real binary:

```
$ praxis -t -c conflict.yaml
invalid configuration: pipeline validation failed for listener 'http':
pipeline contains multiple cluster-selecting filters before load_balancer
(router, llm_d_sc); only the last one's cluster selection will take effect
```

This is correct behaviour — silently letting the last one win would be worse — but it
means path-based routing and content-based routing cannot be combined in one chain
without branch chains. Any deployment wanting both needs a documented pattern.

### F-3. `StreamBuffer` is a whole-chain cost, and it is measurable

A filter that needs the request body forces the entire chain into `StreamBuffer`, so the
whole body is buffered before routing. B-2 measured the cost across body sizes with the
prompt held constant. It is bounded (`max_body_bytes`, default 1 MiB) but it is real, and
it should be stated in any docs for body-derived routing rather than discovered.

### F-4. `access_log` does not render `filter_metadata`

The built-in `access_log` emits a fixed field set. It does log `cluster=`, which *is* the
routing decision, so the classification outcome is observable — but `llm_d_sc.label`,
`llm_d_sc.score` and the model/taxonomy revisions live in `ctx.filter_metadata` and never
reach the log. For an AI gateway, provenance in the access log is the difference between
"we can audit which model revision answered this" and "we cannot".

### F-5. Metric labels sourced from an upstream response are a cardinality vector

Not a Praxis bug — a bug this POC had and fixed, worth flagging because any
enrichment filter can make it. The ranked label is chosen by the *classifier*, so
emitting it as a Prometheus label lets an upstream service mint unbounded series by
growing its taxonomy. `llm_d_sc_route_total` now emits a label only if it appears in the
operator's own route table; anything else collapses to `<unmapped>`. The per-request
header still carries the true label, because a header creates no time series.

## Findings for llm-d-sc

### F-6. One signal per process is the binding constraint

An llm-d-sc instance serves exactly one signal (`LLM_D_SC_CLASSIFIER`) and returns
`INVALID_ARGUMENT` for any `signals` entry that does not match it. An **empty** list is
always accepted, which is what makes a generic client possible — the filter sends `[]` by
default and works against any instance without knowing its taxonomy.

Routing on complexity *and* sensitivity simultaneously therefore needs two deployments
and two filter instances, which the current `check_conflicting_cluster_selectors` rule
makes awkward: only one of them can select a cluster.

### F-7. The complexity classifier generalises across *domains* but not across *task framing*

> **Correction.** An earlier revision of this section said the classifier "has a
> central-tendency bias." That was too broad and unfair to the model, and it is corrected
> here rather than quietly replaced. The classifier is **97.5% accurate**; the effect
> below is a property of prompt *framing*, not a defect in the model.

**First, three things were ruled out before blaming anything:**

1. **The integration is faithful.** All 128 prompts were classified twice — once through
   the full path (client → Praxis → `llm_d_sc` filter → gRPC → llm-d-sc) and once
   straight through `llm-d-sc-classify` with no proxy at all. **128/128 identical
   labels.** The filter extracts the right text and reports exactly what the classifier
   says.
2. **The model is the right one.** The runtime reports
   `model_revision c5f55ef419d268ba843c544dc00988d1e9878044` — the finetuned weights, not
   the un-finetuned MiniLM baseline (whose published accuracy, 62.5%, is close enough to
   the figure below to be a tempting false explanation).
3. **The published accuracy reproduces exactly.** Running llm-d-sc's own held-out set
   (`evals/datasets/complexity-heldout.jsonl`, n=80) through the same binary and the same
   model directory gives **78/80 = 97.5%**, boundary cases 95.0%, and the identical
   confusion matrix (COMPLEX→MEDIUM = 2) as the published table. Nothing about this
   environment is degraded.

**So both numbers are correct, and they measure different things.**

| Prompt set | n | Accuracy |
|---|---:|---:|
| llm-d-sc's own held-out set | 80 | **97.5%** |
| This POC's independently-authored set | 128 | **68.8%** |

The difference is **task framing**, not subject domain. llm-d-sc's held-out COMPLEX
prompts vary the domain widely — vineyard irrigation, festival ticketing, bus fleets,
warehouse robotics, marine telemetry, sailing regattas — but every one of them keeps the
anchors' *framing*: "**Design/Architect/Build a … system** with A, B and C."

The COMPLEX prompts this POC's set gets wrong keep the complexity but change the framing
to planning, operational or creative documents:

```
[MEDIUM 0.996] Lay out the floor plan, equipment list and morning workflow for a 40 seat bakery.
[MEDIUM 0.992] Draft an emergency response plan for a rural elementary school ... roles and drills.
[MEDIUM 0.999] Produce a season long periodisation plan for a college swim team ...
[MEDIUM 0.999] Write a screenplay treatment with three act structure, character arcs and ten scenes.
```

All twelve COMPLEX anchors are technical system-design tasks; all twelve REASONING
anchors are formal proofs and derivations. The embedding space has therefore learned
**"complex *engineering* task"** rather than "complex task", and **"formal proof"** rather
than "reasoning". A genuinely hard planning document is semantically nearer the MEDIUM
anchors than the COMPLEX ones.

**This is a fixable, anchor-level issue, and llm-d-sc already ships the mechanism**: a
custom taxonomy definition can be supplied by path with no rebuild. Adding COMPLEX
anchors with planning/operational/creative framing is the obvious remedy, and it needs no
retraining.

**Why it still matters for a gateway.** The 128-prompt set was written to look like
traffic a real AI gateway receives — 91 domains, deliberately not templated. Whatever the
label is *called*, a gateway operator will read "COMPLEX" as "send this to the big model",
and on that traffic mix the routing outcome was:

```
intended      ->small  ->large   expected
SIMPLE             32        0   small     32/32
MEDIUM             31        1   small     31/32
COMPLEX            16       16   large     16/32
REASONING          12       20   large     20/32
```

Routing accuracy **77.3%**. But the two error directions are not symmetric and must never
be netted:

* wasted capacity (easy prompt → 284 B model): **0.8%**
* **quality risk (hard prompt → 27 B model): 21.9%**

16/32 COMPLEX and 10/32 REASONING prompts came back `MEDIUM`.

**Two consequences that generalise beyond this classifier:**

**(a) The label→cluster mapping is the safety knob, not the classifier.** Re-scoring the
identical classifier output under different mappings:

| mapping | accuracy | wasted capacity | quality risk |
|---|---:|---:|---:|
| `MEDIUM→small` (as deployed) | 77.3% | 0.8% | **21.9%** |
| `MEDIUM→large` (safety-biased) | 78.1% | **20.3%** | 1.6% |
| only `REASONING→large` | 65.6% | 0.8% | 33.6% |

Accuracy moves by 0.8 points while the error profile **inverts**. Headline accuracy is
close to useless for making this choice; only the directional costs are decision-relevant.

**(b) `min_score` cannot fix it.** Misrouted hard prompts scored a median of **0.9919**
against 0.9976 for correctly-routed ones, with fully overlapping ranges (0.8662–0.9993 vs
0.5803–0.9996). The classifier is not hedging on the ones it gets wrong — it is
confidently wrong. A confidence floor is the first knob an operator would reach for, and
on this evidence it would accomplish nothing.

**Caveat, stated plainly:** the intended tiers are the author's labels on prompts the
author wrote. Some of this gap is two humans disagreeing about what "COMPLEX" means
rather than classifier error. n=32 per class. This is a directional finding from one
homelab, not a benchmark result about the model.

## Honest limitations

* One operator, one homelab, **not independently reproduced**.
* v0.1 scope: one signal, h2c only (no TLS to llm-d-sc), no streaming, no
  response-phase classification, no filter-side cache (llm-d-sc already has a
  revision-keyed one; a second would risk serving a stale revision).
* The two model backends are single-replica llama.cpp servers on a shared cluster, so
  end-to-end concurrency was deliberately held at 1.
* Routing accuracy rests on a 128-prompt set authored by the same person who assigned
  its labels.
